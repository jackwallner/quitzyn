Bugs, worst first

B1

One failed database open hides the quit date and the whole history for good, with no message and no way back

highplausibledata
Impact

The user sees a brand new app: counter, check-ins, journal and garden are gone from their point of view. Only a developer can recover them from the aside files.

How it happens
  1. Have a store with months of history.
  2. Launch the app at a moment when ModelContainer init throws (for example a nearly full disk that cannot create the WAL, or a failed migration after an update).
  3. The store and its -wal and -shm files are renamed to Sober.v2.store.unopenable-<stamp>.
  4. The fresh container is empty (or in memory if disk is still full), so onboarding appears again.
  5. Next launch with free space opens the new empty store; the old file is never read again.
Where
Shared/Services/DataService.swift:23Shared/Services/DataService.swift:31Shared/Services/DataService.swift:36
Suggested fix

Retry the open once before moving anything, keep the original in place when the second open fails for a non-corruption reason, and on a later launch offer to restore the newest .unopenable store when the live one is empty.

Evidence
// Unopenable store (corruption or a failed migration). Move it aside
// rather than deleting it...
let stamp = Int(Date.now.timeIntervalSince1970)
for suffix in ["", "-wal", "-shm"] {
    ...
    try? FileManager.default.moveItem(at: file, to: aside)
}

The code treats every nil from try? ModelContainer as corruption. A transient failure takes the same path as a corrupt file, and nothing in the repo reads an .unopenable-* file back (grep finds only the line that writes it).

Not proven: No trigger was reproduced. The evidence is the code path: any failed open is treated as corruption, the store is moved aside, and nothing reads it back. Sober, built from the same code, has the same finding.
