## For the reviewer

- B1 is the riskiest change: it runs before every launch. With no `.unopenable-*` file present it costs one directory listing. With one present it opens the live store and the aside store once each launch until one of them is put back or the live store gains history. A user who already re-onboarded into a fresh store keeps it; the old store stays aside (see below).
- B1's red tests use a seam (`DataService.openStore` with an injected opener) that was first written at the old behavior, so the red run measured the old algorithm.
- B7 could not be shown with a real background trip: on the simulator under XCUITest the app kept running for 40 s in the background and the old code counted the whole time (RED_UI1, countdown 1:15). A 20 s main-thread stall makes the timer miss its ticks the same way suspension does. On a device, suspension is the trigger.
- B3's red failures stop at the note field, which disappears before the test reaches its own assertion; the attached UI tree shows why (the trial sheet replaced the note sheet). The green run walks the whole flow, including the pitch arriving after Save.
- B2's table is magnitudes, not exchange rates. A currency not in it keeps the dollar scale.
- The B9 model change adds an optional attribute; the upgrade test opens a store written without it.

## Needs Jack

- B1 leaves one case open by design: a user whose store was moved aside by an earlier build and who then onboarded again has history in both stores. The app keeps the new one. Merging or offering a choice is a product decision.
- B4 leaves achievements unlocked during the mistaken date in place. Revoking an achievement is a product call.
